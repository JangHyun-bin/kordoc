# 공개 문서 비교에서 확인한 변환 누락

기준: npm `kordoc@4.22.2`, main `b964335`. 문서 전체가 완벽하게 복원됐다는 판정이 아니다. 아래 두 사례를 영상 사전검증 중 원본과 최종 Markdown으로 대조했다.

## HWP5: 공동 한계수량을 연결하는 선

원본은 「관세법 제71조에 따른 할당관세의 적용에 관한 규정」 별표3, 2026-06-30 개정본이다. 기관 제공 PDF는41쪽이다.

- [공식 HWP](https://www.law.go.kr/LSW/flDownload.do?flSeq=166193699), SHA256 `6ec5473ed801bae2ba7bf46c0842412859b7386c4d65148ec345be851537129d`
- [공식 PDF](https://www.law.go.kr/LSW/flDownload.do?flSeq=166193701), SHA256 `8a0c0e87e87ebfe839f61e5520783da141fa6b5fba0ed5bb12049198b245ea54`

PDF1~4쪽의 21,000톤·200,500톤·커피의 ‘수입 전량’은 좁은 별도 열의 괄호선으로 공통 범위를 나타낸다. 수량 셀의 rowspan만으로 범위를 판단하면 안 된다. 예를 들어 커피 수량의 rowspan2는 첫 품목 자체의 두 원시 행만 덮으며, 다음 디카페인 품목까지 덮지 않는다.

재현:

```sh
npm ci
npm run build
node dist/cli.js /path/to/quota.hwp --html-tables -o /tmp/quota-visual.md
node dist/cli.js /path/to/quota.hwp --html-tables --keep-layout-tables --keep-empty-cols -o /tmp/quota-keep.md
node --import tsx --test tests/table-rule-rows.test.ts
```

원본 HWP5는502행9열, 명시셀3,239개다. DocInfo의 BORDER_FILL을 통해 좁은 열7의 선이 `CELL_EDGES`까지 전달된다. 원시 셀 `(28,7)`은 빈 문자열이지만 네 변이 있고 두 행에 걸친 괄호 중심 셀이다.

확인한 문제는 두 단계다.

1. 기본 visual 모드의 빈행 접기가 괄호 중심 셀을 삭제한다. **이 PR은 가로·세로 선이 만나며 다음 행까지 걸친 빈 셀을 보존하도록 수정한다.** 한 행짜리 여백과 연속 세로선만 있는 행은 계속 접는다. 회귀 테스트는 수정 전 실패하고 수정 후 통과한다.
2. HTML 직렬화가 원본 셀의 보이는/없는 변과 좁은 열의 기하를 출력하지 않는다. **이 부분은 아직 해결하지 않았다.** 빈 셀을 보존하는 수정만으로 공동 수량의 Markdown 의미 보존이 완성됐다고 주장하지 않는다. 원문 병합을 임의로 늘리거나 수량을 다른 품목에 추론 배치하는 해결은 피한다.

후속 수정은 원본 변·기하의 IR 직렬화, 선을 출력하는 HTML, `roundtrip/markdown-units.ts`의 HTML 재현 계약을 함께 다뤄야 한다. CSS를 제거하는 뷰어의 한계도 명시해야 한다.

## PDF: 유니코드 없는 번호 기호

원본은 정책브리핑 「청년일자리 회복방안」23쪽 PDF다. [공개 게시물](https://www.korea.kr/briefing/pressReleaseView.do?newsId=156775932).

- PDF SHA256: `d9f4f07b6e33604f4c1ad0d85b2d1b76089a2292dd21fd8312ea2f8ef0ef5e78`
- 대응 원본 HWPX에는 `U+F02B1`~`U+F02B6` 번호6종이 있다.
- PDF의2·9쪽에서 해당6종이 반복되어 총12곳이 누락된다. 같은 쪽의 삼각 글머리표는 별개이며 복원된다.

PDF ToUnicode는 서로 다른 번호 CID10·12·14·15·16·17을 모두 `U+F000`으로 내보낸다. 내장 원본 폰트에는 cmap/post가 없어 원래 사설 코드를 그대로 역산할 수 없다. PDF.js의 임시 `fontChar` 번호를 문자에 하드코딩해서는 안 된다.

현재 `pdf/symbol-glyphs.ts`는 숫자 윤곽을 분류하지 못하고, `pdf/text-clean.ts`가 남은 F000을 제거한다. 이 미지원은 기존 `tests/pdf-symbol-glyphs.test.ts`에도 명시돼 있다. **이 PR은 번호 복원 완료를 주장하지 않는다.** 범용 숫자 윤곽/OCR 인식이나, 복원하지 못한 기호의 페이지·개수를 알려주는 진단이 필요하다.

## 검증 범위

숫자 텍스트와 셀 개수가 맞아도 선이 나타내는 적용 범위는 누락될 수 있다. 원본 HWP 레코드와 공식 PDF의 선을 함께 확인해야 한다. 모수·정답·평가기·제외 조건을 바꾸어 이 두 누락을 성공으로 계산하지 않는다. 실제 기관 문서는 저장소에 추가하지 않았고 합성 회귀 fixture만 포함한다.

- 전체 테스트: 3,994개 중 3,985개 통과, 9개 스킵. 타입 검사·빌드 통과.
- 관련 표·누름틀·열린 하단 회귀 테스트: 38/38 통과.
- 기존 annex 게이트는 실패한다. HWP 표 완전 일치 345/346, cell F1 0.99976이며 PDF는342/346이다. HWP 불일치는 이 할당관세 문서 한 건이다.
- 같은 채점기로 기준 `b964335`를 별도 빌드해 해당 문서는416×9, cell F1 1임을 확인했다. 수정본418×9은 원시 `(28,7)`과 `(374,7)`의 두 빈 병합 모서리 셀을 새로 남긴 결과다. 제거된 원시 anchor는 없다. 기존 정답과의 불일치를 숨기거나 정답을 변경하지 않았으며, 이 PR은 후속 선 출력·정답 계약 검토가 필요한 Draft다.
